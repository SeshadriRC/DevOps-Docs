# The Cinderella Outage

## Incident Details

| Field | Value |
|-------|-------|
| **Severity** | SEV-2 (High) |
| **Service** | Core Backend / Database |
| **Duration** | 15 Minutes (Recurring Daily) |
| **Status** | Resolved |
| **Owner** | Infra/SRE Team |

---

## 1. Issue Summary

For the past 3 days, the primary backend server became unresponsive daily between 02:15 AM and 02:30 AM. Monitoring tools showed "No Data" during this window. SSH access was denied. The server spontaneously recovered at 02:30 AM without intervention.

---

## 2. Business Impact

### User Impact
Night-shift users and international traffic experienced total service unavailability for 15 minutes.

### Data Impact
No data loss, but scheduled nightly batch jobs failed and had to be manually retried.

---

## 3. Root Cause Analysis

**Why did the server hang?**  
The root filesystem (/) reached 100% utilization, preventing the OS from writing lock files or logs.

**Why did the disk fill up?**  
A race condition occurred between the Logging Service and the Backup Script.

### Detailed Findings
The application was running in DEBUG mode, generating massive log files in `/var/log`. Simultaneously, the nightly backup script ran at 02:00 AM, creating a large temporary .zip file on the same partition.

**Disk Space Calculation:**
- Logs: 15GB
- Temp Backup: 10GB
- Total Disk Space: 20GB
- **Result:** Logs (15GB) + Temp Backup (10GB) > Total Disk Space (20GB)

### Root Cause
**Resource Contention.** Lack of partition isolation between OS, Logs, and ephemeral backup data.

---

## 4. Resolution & Fix

### Immediate Fix
- Manually truncated old log files
- Changed Application Log Level from DEBUG to INFO

### Permanent Fix
- Re-configured the backup script to stream data directly to S3 (or use a separate `/tmp` volume) instead of writing to the root disk
- Implemented aggressive logrotate policies (daily rotation + compression)

---

## 5. Action Items

- **[High]** Repartition servers to separate `/var/log` and `/data` from the root OS (`/`)
- **[Low]** Audit all cron jobs for temporary file cleanup logic

# Immediate Fix

## Truncate Large Logs

Check:

```bash
ls -lh /var/log/application.log
```

Output:

```text
14G application.log
```

Truncate:

```bash
truncate -s 0 /var/log/application.log
```

or

```bash
> /var/log/application.log
```

Space immediately returns.


## Reduce Logging

Change:

```properties
logging.level.root=DEBUG
```

to:

```properties
logging.level.root=INFO
```

Restart application:

```bash
systemctl restart app
```


# Permanent Fix #1: Log Rotation

Install/configure logrotate.

Example:

```bash
cat /etc/logrotate.d/application
```

```text
/var/log/application.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
}
```

What happens?

```text
application.log
application.log.1
application.log.2.gz
application.log.3.gz
```

Old logs compressed automatically.


# Permanent Fix #2: Stream Backup Directly to S3

Bad:

```bash
zip backup.zip /data
aws s3 cp backup.zip s3://bucket
```

Needs local disk.

Better:

```bash
tar cz /data | aws s3 cp - s3://bucket/backup.tar.gz
```

Flow:

```text
Data
 |
tar
 |
AWS S3
```

No large temporary file on disk.


# Permanent Fix #3: Separate Partitions

Bad:

```text
20GB /
```

Everything shares one disk.

Better:

```text
20GB /
50GB /var/log
100GB /data
```

Now:

```text
Logs fill /var/log
```

but:

```text
OS remains healthy
```

# Interview Answer

> The server became unavailable because the root filesystem reached 100% utilization. The application was running in DEBUG mode, generating approximately 15GB of logs, while a nightly backup job created a temporary 10GB archive on the same 20GB partition. This exhausted disk space, preventing the operating system from creating lock files and logs, which caused SSH and monitoring failures. We confirmed the issue using `df -h`, `du -sh`, cron inspection, and system logs. As an immediate fix, we truncated old logs and reduced the log level from DEBUG to INFO. Long-term, we implemented logrotate, streamed backups directly to S3, and planned separate partitions for OS, logs, and application data.

## 1. In the script I don't see the removal of the zip file

You're right.

The example I showed:

```bash
#!/bin/bash

zip -r backup.zip /data
aws s3 cp backup.zip s3://company-backup
```

does **not** remove the file.

A real script would usually have:

```bash
#!/bin/bash

zip -r backup.zip /data

aws s3 cp backup.zip s3://company-backup

rm -f backup.zip
```

or

```bash
#!/bin/bash

BACKUP_FILE=/tmp/backup_$(date +%F).zip

zip -r $BACKUP_FILE /data

aws s3 cp $BACKUP_FILE s3://company-backup

rm -f $BACKUP_FILE
```

### Then why did the server recover automatically?

The incident description says:

> "The server spontaneously recovered at 02:30 AM"

That suggests one of these happened:

**Scenario A (most likely)**

The backup script cleaned up the temporary file after upload:

```bash
zip
↓
upload to S3
↓
rm backup.zip
```

Disk usage dropped and the server recovered.

**Scenario B**

The backup process used a temporary file that was automatically deleted when the process completed.

**Scenario C**

A cleanup cron job removed old temporary files.

The RCA doesn't explicitly show the cleanup step, but for the server to recover automatically, something must have freed space.

## 2. Where is the logging level changed?

This depends on the application.

### Spring Boot

In:

```text
application.properties
```

or

```text
application.yml
```

Example:

**Before**

```properties
logging.level.root=DEBUG
```

**After**

```properties
logging.level.root=INFO
```

or

```yaml
logging:
  level:
    root: INFO
```

---

### Kubernetes Environment Variables

Sometimes developers externalize it through a ConfigMap.

ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: payment-config

data:
  LOG_LEVEL: INFO
```

Deployment:

```yaml
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: payment-config
        key: LOG_LEVEL
```

Application reads:

```java
System.getenv("LOG_LEVEL");
```

---

### Java Logback

Sometimes logging is controlled through:

```text
logback.xml
```

Example:

```xml
<root level="DEBUG">
```

Changed to:

```xml
<root level="INFO">
```

---

### Linux Application

Could also be in:

```text
/etc/myapp/config.ini
```

Example:

```ini
log_level=DEBUG
```

changed to:

```ini
log_level=INFO
```

---

### How would a DevOps engineer find it?

On a Linux server:

```bash
grep -Ri "DEBUG" /opt/app/
/etc/
/app/
```

or inside a pod:

```bash
kubectl exec -it <pod-name> -- sh

grep -Ri "DEBUG" .
```

or inspect environment variables:

```bash

```

Look for:

```text

```

### Interview Answer

If asked *"Where did you change DEBUG to INFO?"*, a safe answer is:

> We identified that the application was running with DEBUG logging enabled. Depending on the application framework, the logging level was updated in the application's configuration (such as `application.properties`, `application.yml`, `logback.xml`, or a Kubernetes ConfigMap) from `DEBUG` to `INFO`, and the application was restarted to apply the change.
